## 0. この文書について

### 0.1 位置づけ

- 本書は、参照元の再受験と経年比較（2026-11-04 取得）をアプリに再現するための領域別仕様書で、M7 の総括 `docs/基本設計/11_参照元の更新への追従.md` の下に置く。実装担当が本書と、本書が名前を挙げた 11-6 の節を見て、再受験のつながり・経年比較のタブの 11-7 の状態・1 年経過の帯・組み合わせの API・印刷の形を作れる粒度で書く。
- 前回の仕様（要件定義書・付録A〜E・基本設計 00〜10）とアプリには、再受験・前回の結果・経年比較の記述も実装も無い。本書は新しい機能を足すもので、既存の分冊は 4 章のとおり改版する。既存の分冊と食い違うときは本書を正とする。
- 経年比較の AI の部分は 11-6 が定める: 機械的な計算（11-6 §2.6.2。純関数 `lib/presentation/longitudinal-calc.ts`）、AI への入力文（11-6 §2.6.3）、生成の流れ・状態・作り直し（11-6 §2.6.4・§3.4・§3.5）、表示権限（11-6 §2.6.5）、作成中と表示制限の表示（11-6 §2.6.6）、レポート（11-6 §2.6.7）、育成・定着との連携（11-6 §2.6.8）、プロンプト（11-6 §2.7）、出力のスキーマ（11-6 §2.8.3）、状態の項目（11-6 §3.1・§3.2）、応答の形 `LongitudinalAiDto`（11-6 §3.6）、印刷（11-6 §2.12）。タブの状態の分担は 11-6 §2.6.1 の表のとおりで、本書は 11-7 の担当の状態と、状態を選ぶ部品 `LongitudinalPanel` を定める。本書は 11-6 の関数・部品・応答を使い、同じものを別に作らない。
- 選択肢は書かない。依頼主の決定（10 の K-20〜K-40）を当てはめた最終の仕様だけを書く。参照元と変える箇所は「参照元: …／アプリ: …（K-xx）」と書く。
- 推定は「推定」、取得物から分からないものは「未確認」と書き、6 章にまとめる。

## 2. 仕様

### 2.1 全体の流れ

```text
[1回目の結果詳細] 経年比較AI解説タブ: ロック画面「再受験を依頼する」 ─────┐
[1回目の結果詳細] 枠の上の 1 年経過の帯「再受験を依頼する」 ─────────────────┴→ 専用リンク画面（リンクをコピー）
        │ 管理者が本人に送る
        ▼
[受験者登録] {サイトの URL}/exam?q={organizationId}&p=executives&prev={1回目の resultId}（11-1 §2.2.8）
        ▼
[送信] 新しい受験の previousResultId = 1回目（条件を満たすときだけ。11-1 §2.7.3）。既存スタッフ・区分は在籍
        ▼
[2回目の結果詳細] 経年比較AI解説タブ: 確認画面「✦ 経年比較レポートを作成する」（本書）
        → 生成・作成中・レポート（11-6 §2.6.4・§2.6.6・§2.6.7）
[回答一覧] 1 行にまとめる（最新 = 2回目）。「2回目」「経年比較あり」、⋮「以前の受験」（11-2）
```

- 別の道: 専用リンクを使わずに受けた受験は、どちらかの結果詳細の組み合わせ画面で手動でつなぐ（§2.10）。
- 2 回目以降の結果から次の再受験を頼む入口は、受験から 1 年たって出る帯だけ（K-39 Q-36。§2.9）。

### 2.2 前回の結果のつながり（keinen-01・keinen-M3・ai-23、Q-35）

#### 2.2.1 前回の結果と有効な前回

- 参照元: 回答データの「前回の回答」。受験者登録で URL の `prev` の回答を受験者 User の「再受験元の回答」に入れ、送信のときに新しい回答データの「前回の回答」に写す。または組み合わせ画面で手動で入れる（参照元定義の kh_link）。「同じ人の受験」は前回の回答でつながった受験の並びだけで決め、氏名の一致は組み合わせのときの並び順と警告にだけ使う（参照元定義の kh-app）。
- アプリ: `results.previousResultId`（§3.1）。書くのは 11-1 の送信（`submitSession()`。作成のときに 1 回）と、本書の手動の組み合わせ（`linkPreviousResult()`。§3.5.3）の 2 つだけ（§3.4 の I-M7-K1）。
- 有効な前回: `previousResultId` が `null` でなく、その文書があり、`organizationId` が今回と同じで、`deletedAt == null` のもの。経年比較のタブ（11-6・本書）・1 年経過の帯・回答一覧（11-2）・母集団（11-5）・組織内分類（11-3）は、すべて有効な前回だけを「前回」として扱う。
- 同じ人の判定に氏名・電話番号を使わない（参照元どおり）。氏名の一致は、組み合わせ画面の並び順と「氏名が違います」の札、確認画面の警告にだけ使う（§2.10、§2.11）。

#### 2.2.2 前回をつなぐ経路と条件

| 経路 | いつ | つなぐ条件（どれも K-31 ①） | 書くもの |
|---|---|---|---|
| 再受験リンク | 登録で前回の候補を受け付け、送信で確定する | 11-1 §2.2.8・§2.7.3（同じ組織・論理削除されていない・まだほかの受験の前回になっていない） | 新しい受験の `previousResultId`（作成のとき） |
| 手動の組み合わせ（今回より新しい候補を選ぶ） | 組み合わせ画面で「この組み合わせで決定する」 | §3.5.3 の条件。今回に次の受験が無く、候補に有効な前回が無く、候補が生成中・生成済みでない | 候補の `previousResultId` = 今回 |
| 手動の組み合わせ（今回より古い候補を選ぶ） | 同上 | §3.5.3 の条件。候補がまだほかの受験の前回になっておらず、今回が生成中・生成済みでない（11-6 §3.3 の I-ai-3） | 今回の `previousResultId` = 候補（今の前回があっても置き換える。レポートを作るまでは選び直せる） |

- どの経路でも、1 つの受験を前回とする（論理削除されていない）受験は 1 つまで（§3.4 の I-M7-2。枝分かれを作らない。keinen-M3）。参照元は同じ再受験リンクで 2 回受けると、同じ前回を持つ受験が 2 つでき、回答一覧に「2回目」の行が 2 つ出る（参照元の不具合と同じ扱い。K-31 ①）。
- 新しい側の受験日は古い側より後（§3.4 の I-M7-1）。
- 新しい側の経年比較の状態が生成中（滞留していない）・生成済みなら、組み合わせを拒む（11-6 の I-ai-3）。失敗なら、前回を書くのと同じトランザクションで生成前に戻す（§2.10.4）。

#### 2.2.3 前回が削除されたとき（K-39 Q-35）

- 参照元: 定義に無い（回答一覧の削除はその回だけで、つながりが切れると推定）。
- アプリ:
  - 受験の論理削除（11-2 §2.16・§3.7）で、ほかの受験の `previousResultId` を書き換えない（K-04）。
  - 前回が論理削除された受験は「前回なし」として扱う（11-6 §2.6.5 と同じ）。経年比較のタブは前回なしの状態（ロック画面・新しい受験の案内・表示制限のどれか。§2.4）になり、確認画面とレポートを出さない。保存済みのレポート（`aiAnalyses` と経年比較の状態）は消さず、表示しない（11-6 の `latest` が `null`）。回答一覧の「経年比較あり」も付かない（11-2 §2.9）。
  - 前回なしになった受験は、次の受験が無ければ再受験を依頼できる（専用リンク画面）。組み合わせ画面で新しい前回を選べるのは、その受験の経年比較の状態が生成中・生成済みでないときだけ（11-6 の I-ai-3。レポートを作った受験は前回を選び直せない。参照元も保存内容がある受験は組み合わせを変えられない）。
  - 次の受験が論理削除されると、今回は「次の受験なし」になる（再受験の依頼・1 年経過の帯・組み合わせの候補の条件に戻る）。
  - 例: A（1回目）と B（2回目。前回 = A）。オーナー以外の管理者の回答一覧では、既存スタッフの B が見えないので A が行の代表になり、A を削除できる（11-2 §2.2・§2.16）。このときオーナーが開く B の経年比較はロック画面になり、作成済みのレポートは出ない。

#### 2.2.4 次の受験と受験回の並び

- 次の受験: 今回と同じ組織で `previousResultId == 今回の resultId` かつ `deletedAt == null` の受験（受検者区分を問わない。閲覧者に見えない既存スタッフの受験も含む）。I-M7-2 により 0 件か 1 件。読むのは 11-6 §3.7.9 の `findNextResult`（Q-M7-1。1 件まで）。
- 見える次の受験: 次の受験が閲覧範囲にあり、`submittedAt` が今回より後のもの（参照元定義の kh-app の newerOf と同じ。11-6 §2.6.5 の「見てよいか」）。
- 受験回の並び（応答の `links.exams`）: 次の手順で、閲覧範囲の受験だけを古い順に並べる（参照元定義の kh-app の chain）。
  1. 並び = [今回]。
  2. 古い側: 今回の有効な前回から、`previousResultId` を順にたどって先頭に足す。たどった受験が閲覧範囲に無い・有効でない（文書が無い・組織が違う・論理削除済み）・すでに並びにある、のどれかで止める。たどる回数は 50 回まで（読み取りの上限。I-M7-1 により輪はできない）。
  3. 新しい側: 並びの最後の受験の次の受験を末尾に足すことを、最大 20 回繰り返す（参照元どおり）。次の受験が無い・閲覧範囲に無い・すでに並びにある、のどれかで止める。
- 受験回の番号 n は並びの中の位置 + 1。オーナー以外の管理者には既存スタッフの受験が並びに入らないので、番号は閲覧範囲の中での番号になる（参照元どおり）。

### 2.3 表示制限（keinen-05・ai-22・ai-M3、K-29）

- 参照元: 見ている人がオーナーでなく、今回または前回の受験が既存スタッフ（前回が一覧に見つからないときも既存スタッフとみなす）なら、経年比較を出さない。前回が無く、次の受験はあるが見えない（既存スタッフ）ときも同じ画面。受験回の切り替えと組み合わせの候補でも、オーナー以外には既存スタッフの受験を出さない（参照元定義の kh-app の read・decide。ソースのコメント「既存スタッフ（回答者情報-幹部 = yes）の受験は、オーナー（院長）にだけ表示します。」）。
- アプリ: 次の 2 つを表示制限にする。判定はサーバ。
  - 状態 1: 閲覧者がオーナーでなく、今回か有効な前回が既存スタッフの受験（11-6 §2.6.5。応答の `access: "hidden"`）。今回が既存スタッフなら、オーナーでない管理者はそもそも結果詳細を開けない（404。04 D04-07）ので、実際には前回が既存スタッフのとき。
  - 状態 7（本書）: 有効な前回が無く、次の受験があり、それが見えない（応答の `next.visible` が偽）。
- 参照元: 一覧に見つからない前回・次の受験を既存スタッフとみなす／アプリ: サーバが文書を読んで判定する。前回が見つからないのは論理削除・別の組織のときだけで、それは「前回なし」（§2.2.3）。
- 再受験の受験は既存スタッフ扱い（K-39 Q-33）なので、オーナーでない管理者が求職者として受けた 1 回目を開くと、2 回目（既存スタッフ）があれば状態 7 になる。
- 役職の変更（11-2 §2.15・§3.2）で受検者区分が変わると、次に読んだときからそれに従う（K-39 Q-02）。
- 画面: 11-6 の部品 `LongitudinalHiddenNotice`（11-6 §2.6.6。見出し「このスタッフの経年比較は、責任者のアカウントでのみ表示されます」、本文「必要な場合は、責任者にご確認ください。」）だけを出す。受験回の切り替え・ボタンは出さない。
- 表示制限（状態 1・7）のとき: 応答の `links` は空（`exams` が `[]`、`nextResultId`・`reexamLink` が `null`。§3.5.1）、組み合わせの候補は空（§3.5.2）、組み合わせの要求は 409（`hidden`。§3.5.3）。
- 1 年経過の帯（§2.9）はこの判定を見ない（参照元どおり）。表示制限の受験で帯を押すと、経年比較のタブが表示制限で開く。

### 2.4 経年比較のタブの状態の決め方（keinen-04）

- AI 解説の領域（11-6）で「経年比較AI解説」のタブを選ぶと、経年比較のパネル（§3.9 の `LongitudinalPanel`）を出す。データは結果詳細のページ（Server Component）が作った経年比較の応答（`AiAreaDto.longitudinal`。§3.5.1 の `links` を含む）で、パネルはこれを 11-6 のフック `useAiGeneration("longitudinal", initial)` に渡し、フックの今の値で描く。タブを開いたときに読み直しはしない（作成中の読み直しは 11-6 §2.3.5、組み合わせのあとは §2.10.4 の応答）。
- 状態は 11-6 §2.6.1 の表の順で、上から最初に当てはまるものを出す（`decideLongitudinalScreen`。§3.8）。

| 順 | 状態 | 条件（応答とパネルの値） | 部品 | 担当 |
|---:|---|---|---|---|

### 2.14 読み上げ・焦点・先頭まで戻す

- 読み上げ: パネルの中に見えない通知の領域を 1 つ置く（`role="status"`、`aria-live="polite"`、`.sr`）。次のときに、いったん空にしてから文を入れる（同じ文でも読み上げるため。参照元は 50 ミリ秒後に入れる）。作成中・レポートができたときの読み上げは 11-6 §2.6.4。

| とき | 文 |
|---|---|
| 組み合わせ画面を出した | 別の受験を選ぶ画面です |
| 専用リンク画面を出した | 再受験のリンクを発行する画面です |
| 確認画面を出した（タブを開いたときを含む） | レポートを作成できる状態です |
| 組み合わせを決定した | 組み合わせを決定しました |
| 専用リンクのコピーの成功・失敗 | コピーしました／コピーできませんでした |

```ts
// lib/services/schemas/admin-longitudinal.ts
export const linkLongitudinalInputSchema = z.strictObject({ otherResultId: docIdSchema });
export type LinkLongitudinalInput = z.infer<typeof linkLongitudinalInputSchema>;
```

処理（`linkLongitudinalPrevious(ctx, resultId, input)`）:

1. 本文を検証する（422 `VALIDATION_ERROR`。`otherResultId` がパスと同じでも 422）。今回を `loadVisibleResult` で読む。相手を `getResult({ resultId: otherResultId, viewer })` で読む（閲覧範囲に無ければ 404 `RESULT_NOT_FOUND`）。
2. 今回が表示制限（§2.3 の状態 1・7。`loadLongitudinalPair`）なら 409 `LONGITUDINAL_LINK_CONFLICT`（`reason: "hidden"`）。
3. 受験日の新しい方を新しい側 N、古い方を古い側 O とする。同じなら 409（`reason: "same_time"`）。
4. `linkPreviousResult({ newerResultId: N, olderResultId: O, viewedResultId: 今回, viewer, staleAfterMs: AI_STALE_AFTER_MS, meta })`（§3.8。トランザクション）:
   1. 読む（書く前にすべて）: N と O の文書。Q-M7-1 で O を前回とする論理削除されていない結果（limit 2）。N の `previousResultId` の文書（`null` でなければ）。
   2. N・O が無い・組織が違う・論理削除済み・閲覧範囲に無い → `RESULT_NOT_FOUND`。
   3. N の `previousResultId` がすでに O → 何もしない（`{ changed: false }`。監査ログも書かない）。
   4. O を前回とする結果が N 以外にある → `already_linked`。
   5. 今回が O（新しい候補 N を選んだ）なのに、N に有効な前回がある → `has_previous`。
   6. N の経年比較の状態が `generating`（滞留していない）→ `generating`。`completed` → `completed`（11-6 の I-ai-3）。
   7. 書く: N の `previousResultId = O`、N の経年比較の状態が `failed` か滞留した `generating` なら生成前（§3.2）、N の `updatedAt`、O の `updatedAt`（I-M7-2 の直列化）、監査ログ `result.longitudinal_link`。
5. 応答: `getAiState(ctx, 今回, "longitudinal")`（11-6。監査ログを書かない）。

| HTTP | code | 条件 |
|---:|---|---|
| 404 | `NOT_FOUND` | パスの `resultId` が文書 ID の形でない |
| 404 | `RESULT_NOT_FOUND` | 今回か相手が閲覧範囲に無い（他組織・論理削除済み・オーナー以外に対する既存スタッフ） |
| 409 | `LONGITUDINAL_LINK_CONFLICT` | `details.reason` が `hidden`・`same_time`・`already_linked`・`has_previous`・`generating`・`completed` のどれか |
| 422 | `VALIDATION_ERROR` | 本文の形が違う、`otherResultId` が文書 ID の形でない・パスと同じ |
| 503 | `SERVICE_UNAVAILABLE` | Firestore の一時的な失敗（トランザクションの再試行の上限を含む） |

- 参照元のサーバの確かめ（kh_link）: 両方が自組織、新しい方の保存内容が空、新しい方が後、古い方がまだ誰の前回でもない。アプリは閲覧範囲・表示制限・新しい候補の前回なし・生成中でないことを足し、保存内容の代わりに経年比較の状態で判定する（§1.4 の 3）。
- 同じ受験に 2 人が同時に別の組み合わせを決めると、トランザクションの直列化で後の方が `already_linked`（または `has_previous`）になる。
