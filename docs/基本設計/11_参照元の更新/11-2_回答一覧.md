## 0. この文書について

### 0.1 位置づけ

- 本書は、参照元の回答一覧の更新（2026-11-04 取得）をアプリに再現するための領域別仕様書で、M7 の総括 `docs/基本設計/11_参照元の更新への追従.md` の下に置く。実装担当が本書だけを見て、回答一覧の API・画面と、それに要るデータ項目を作れる粒度で書く。

- 推定は「推定」、取得物から分からないものは「未確認」と書き、6 章にまとめる。

### 0.3 根拠の書き方

- 参照元の定義: 「参照元定義（2026-11-04 取得）の …」と書き、ページ・再利用要素・HTML アプリ・ポップアップ・ワークフローの名前（必要なら要素 id）で示す。回答一覧の主な定義は、再利用要素 CRM Table View（名前の先頭に絵文字が付く）、その中の HTML アプリ ad-app（一覧の画面のすべてを描く）、データ用 HTML の ad-d1・ad-d2・ad-misc、ポップアップ「Popup: Start / Edit Convo」（削除の確認。要素 id bUkhA）、ポップアップ「Popup: 利用履歴」、受け渡しのワークフロー ad_open・ad_team・ad_excl・ad_stat・ad_role（要素名「JavascripttoBubble B」）・ad_del・ad_hist。
- 参照元の画面: 「参照元の画面（2026-11-04）」。オーナーでない管理者のアカウントで閲覧したもの（回答一覧、利用履歴、受験から1年以上、区分タブ）。⋮メニュー・区分メニュー・入社日と退職日のダイアログ・削除の確認・通知と、オーナーの表示は画面に写っておらず、ad-app の定義（削除の確認はポップアップ「Popup: Start / Edit Convo」の定義）から書いた（6 章）。削除の確認と利用履歴のポップアップの寸法・色・角丸は、参照元のアプリ定義にある各要素の値と、要素が使うスタイル（ポップアップ・ボタン・見出し・本文の各スタイル）と色の定義の値から書いた。
- アプリと前回の仕様: リポジトリのパス（例 `lib/services/result-list.ts`、`docs/基本設計/06_画面設計_管理者.md` §3.4）。

### 0.5 K-19 の置き換え

画面の文言は置き換え後のアプリの文言で書き、置き換えた箇所は（参照元: …）で原文を残す。回答一覧で置き換えるのは「院長」（役職の札・役職のメニュー・役職の通知・職業）と「院長のみ閲覧」（リンクのメニューの補足）だけで、どちらも K-19 の規則どおり「責任者」とする。一覧の文言に「医院」「クリニック」と歯科の職種・業務の語は無い（職業の表示はアプリの職業マスタの名前）。言い換えに迷う文言は無い。

### 2.2 同じ人の受験を 1 行にまとめる（list-01・keinen-18）

参照元: 同じ人とみなすのは「前回の回答」でつながった受験だけで、氏名・電話番号の一致は使わない。ある受験の前回が一覧の中にあり自分自身でなければ、その前回の「次」をこの受験とする（同じ前回を指す受験が 2 つ以上あれば受験日が新しい方）。「次」を持たない受験が行の代表（最新の受験）で、つながりは代表から前回をたどる（一覧に無い受験と、たどり済みの受験で止まる）（参照元定義（2026-11-04 取得）の HTML アプリ ad-app の read）。

アプリ: 次の関数でサーバがまとめる。一覧（§3.5）と更新（§3.6）で同じ関数を使い、在籍・退職（11-3）も使う。

```ts
// lib/services/person-chain.ts（純関数。Firestore に触れない）
export interface PersonChainNode {
  readonly resultId: string;
  readonly previousResultId: string | null;
  readonly submittedAt: Date;
}
export interface PersonRow<N extends PersonChainNode> {
  readonly head: N;              // 代表の受験 = chain[0]
  readonly chain: readonly N[];  // [代表, 前回, 前々回, …]
}
/** 閲覧範囲の受験から行を作る。戻り値は代表の submittedAt の降順（同じなら resultId の昇順） */
export function buildPersonRows<N extends PersonChainNode>(nodes: readonly N[]): readonly PersonRow<N>[];
/** resultId をつながりに含む行（無ければ null） */
export function findPersonRow<N extends PersonChainNode>(rows: readonly PersonRow<N>[], resultId: string): PersonRow<N> | null;
```

`buildPersonRows` の手順:

1. 入力は閲覧範囲の受験（同じ組織・論理削除されていない・オーナー以外は受検者区分が `applicant`。§3.5 の手順 1）だけ。
2. 各受験 r について、`r.previousResultId` が入力の中にあり r 自身でなければ、`nextOf[前回] = r` とする。すでに入っていれば、submittedAt が新しい方（同じなら resultId の昇順で先の方）を残す。
3. 入力を submittedAt の降順（同じなら resultId の昇順）に並べ、自分を前回とする受験が無い受験（`nextOf[自分]` が無い受験）を代表として、順に次の 4 を行う。
4. つながり = [代表]。現在の受験の前回が入力の中にあり、まだどの行にも入っていなければ、それを末尾に足して進む。どれかの行に入っている受験に当たるか、前回が入力に無ければ止まる。
   - 参照元: たどり済みの判定はその行の中だけ（枝分かれのとき前回が 2 つの行に入る）／アプリ: すべての行をまたいで判定する（K-31 ①。枝分かれは 11-7 が書き込みのときに作らないので、通常は結果が変わらない）。
5. 3〜4 のあとで、どの行にも入っていない受験（前回のつながりが輪になったなど、起きないはずのデータ）が残れば、同じ順でそれを代表にして 4 を行う。
6. 行を代表の submittedAt の降順（同じなら resultId の昇順）に並べて返す。

- 閲覧範囲の受験だけでまとめるので、オーナー以外の管理者には、つながりの途中の既存スタッフの受験が入らず、そこでつながりが切れる（参照元どおり。参照元は既存スタッフの受験のデータをオーナーのときだけ描くと推定。再受験は既存スタッフ扱い（Q-33）なので、オーナー以外の一覧では再受験の前の受験が 1 人として残る）。
- 論理削除された受験は入力に入らないので、前回が削除されるとつながりが切れる（Q-35）。行の代表が削除されると、その前回が代表になる。
- 受験回数（n）はつながりの件数。行の表示はすべて代表の受験と、その受検者の値。

import { MANAGER_OCCUPATION_CODE } from "@/lib/masters/occupations"; // = 10「責任者」（K-21。定数は 11-1 が置く）

export function effectiveStaffRole(staffRole: StaffRole | null, occupationCode: number): StaffRole | null {

### 2.13 区分の変更（list-04）

### 2.21 絞り込みの状態の保存（list-24）

- 区分タブ（`seg`）・検索語（`q`）・チーム（`team`）・並び順（`sort`）を、ブラウザの `sessionStorage` のキー `ad-filter` に JSON で保存し、一覧を開き直したとき（結果詳細の「回答一覧に戻る」、サイドメニュー、再読み込み）に戻す。表示の上限は保存しない（戻すと 100）。
- 値: `seg` = `all`・`cand`・`exec`・`left`・`old`、`q` = 文字列、`team` = 空・`none`・`A`〜`Z`、`sort` = `new`・`old`・`name`・`due`。読めない・決まった値でないものは既定（`all`・空・空・`new`）にする。
- 保存の契機: タブ・集計カード 3 番・チームで絞り込む・並び順・絞り込みを解除を操作したとき、検索語は入力から 150 ミリ秒たったとき。
- 読み書きはすべて例外を握りつぶす（ストレージが使えない環境では保存しないだけ）。
- 戻すのは最初の描画のあと（マウントの直後）に 1 回。サーバで描いた最初の表示は既定の状態。
- 戻したチームが今の行で使われていなくても、そのチームで絞ったままにする（選択欄にその選択肢は無く、表示は 0 件の 1 番になり「絞り込みを解除」で戻せる。参照元どおり）。
- 個人情報の扱い: 検索語に氏名・電話番号が入り得るが、`sessionStorage` はタブを閉じると消える。`localStorage` には置かない（06 §2.5）。

### 2.23 つながった全受験への書き込みと表示の更新（list-34・keinen-20・list-32）

- チーム・集計から除外・区分・入社日・退職日・役職の変更は、行の代表の受検者 ID で `PATCH /api/v1/admin/respondents/{respondentId}`（§3.6）を送り、サーバがその受験を含む行のつながり全件（閲覧範囲の中）に、1 回のバッチで書く。参照元: 450 ミリ秒おきに 1 件ずつ送る／アプリ: 1 回のバッチ（Bubble の制約によるもので、結果は同じ）。
- 画面は押した直後に行の表示を変え（参照元どおり）、送信中はその行の操作の要素を `aria-disabled` にして重ねて送らせない（06 §2.5）。
  - 成功: Server Component を読み直し（`router.refresh()`）、サーバの値で表示し直す。区分タブ・検索語・チーム・並び順・表示の上限は保つ。読み直しはメニューが開いている間は待ち、閉じたあとに行う。読み直しても、焦点のある要素と検索欄の入力の位置を保つ（参照元どおり。行の React の `key` は代表の resultId にし、要素を作り直さない）。
  - 失敗: 行の表示を元に戻し、エラーの通知（04 のエラーの文言。通信の失敗は T-33「通信に失敗しました。ネットワーク接続を確認して再度お試しください」）。404 `RESPONDENT_NOT_FOUND`・`RESULT_NOT_FOUND` のときは読み直す。403（停止・未登録）は今の規則どおり再読み込み（06 §10.4）。
- 自動更新: 参照元は 700 ミリ秒ごとにデータを確かめ、新しい受験や保存の結果を再読み込みなしで出す／アプリ: 時間ごとの読み直しはせず、操作のあとと、ページを開き直したときに最新にする（決定事項 1。ブラウザから Firestore を購読しない。一覧は全件を読むので、短い間隔の読み直しは読み取りの回数が多すぎる）。

### 2.24 再受験の直後の表示（list-M2・keinen-M1、Q-34）

## 3. データモデルと API の変更

### 3.1 `results` の項目の追加（K-28・Q-02）

| フィールド | 型 | 必須 | 作成時（送信）の値 | 説明・検証 |
|---|---|---|---|---|
| `employmentStatus` | string | ○ | `respondents.kind` が `applicant` なら `candidate`、`executive` なら `employed`（K-28） | 区分。`candidate`／`employed`／`left` |
| `hiredOn` | string / null | ○ | `null` | 入社日。暦日 `YYYY-MM-DD`（1900-01-01〜2100-12-31 の実在する日） |
| `leftOn` | string / null | ○ | `null` | 退職日。同じ形。`employmentStatus` が `left` のときだけ値を持てる。`hiredOn` と両方あるときは `hiredOn` ≤ `leftOn` |

| HTTP | code | 条件 |
|---:|---|---|
| 404 | `NOT_FOUND` | `respondentId` が文書 ID の形でない |
| 404 | `RESPONDENT_NOT_FOUND` | パスの受検者が閲覧範囲にない |
| 404 | `RESULT_NOT_FOUND` | 受験の無い受検者に `employment`・`staffRole` を送った、つながりが見つからない |

`updatePersonAttributes()` の手順:

1. 書く範囲の受検者を `getAll()` で読み、無い・組織が違う・論理削除済み・閲覧範囲にない受検者を除く（`logger.warn` に結果 ID だけを出す）。残りが 0 件なら `RepositoryError("RESPONDENT_NOT_FOUND")`。
2. 受験（`resultId` があるもの）を `getAll()` で読み、無い・組織が違う・論理削除済みのものを除く。`staffRole` を変えるときは、受検者の `usageLogId` の利用履歴も `getAll()` で読む（ある文書だけを書く）。
3. 受験ごとに、変わる項目だけを書く。
   - `teamCode`・`isExcluded`: `respondents`（正）と `results`（複製）。
   - `employment`: `results` の `employmentStatus`・`hiredOn`・`leftOn`。
   - `staffRole`: `results.staffRole`。受検者区分 = `manager`・`leader` なら `executive`、`staff` なら `applicant`。変わるときは `respondents.kind`・`results.respondentKind`・`usageLogs.respondentKind`。`employmentStatus` の無い受験には、変える前の受検者区分から求めた区分を書く（§3.1）。
4. 書いた文書の `updatedAt` はすべて同じ `Timestamp`（今の I-36 の規則）。変わった項目ごとに監査ログ（§3.10）を同じバッチに積む。
5. 変わる項目が無ければ何も書かない。
