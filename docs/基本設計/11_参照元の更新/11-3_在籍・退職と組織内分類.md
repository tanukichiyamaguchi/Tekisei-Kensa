## 0. この文書について

### 0.1 位置づけ

- 本書は、参照元の組織内分類の作り直しと、在籍・退職の画面の新設（2026-11-04 取得）をアプリに再現するための領域別仕様書で、M7 の総括 `docs/基本設計/11_参照元の更新への追従.md` の下に置く。実装担当が本書だけを見て、2 つの画面・その API・文言マスタの改版を作れる粒度で書く。
- 本書と既存の分冊（06 §1・§2.3・§2.4・§3.6・§4.3・§7・§10.5・§11・§12、04 §3.2・§5.7・§8.2・§8.3・§11、02 §7.1・§8.5・§9.4・§11、00 §3.3・§4.2、付録C §1・§8、付録E §6）が食い違うときは本書を正とし、4 章のとおり各分冊を改版する。
- 区分・入社日・退職日のデータ項目、受検者の更新 API、同じ人の受験をまとめる関数、通知とダイアログの共通部品の改修は 11-2（回答一覧）が定める。本書はそれを使う側として書き、同じことを定め直さない。
- 選択肢は書かない。依頼主の決定（10 の K-20〜K-40・K-49・K-50）を当てはめた最終の仕様だけを書く。参照元と変える箇所は「参照元: …／アプリ: …（K-xx）」と書く。
- 推定は「推定」、取得物から分からないものは「未確認」と書き、6 章にまとめる。

### 0.3 根拠の書き方

- 参照元の定義: 「参照元定義（2026-11-04 取得）の …」と書き、名前で示す。本書の主な定義は次のとおり。
  - 再利用要素「組織内分類」: 見出し行（見出しの文字「text:page-title」、ボタン「Group MZ」）、ポップアップ「Popup: 組織内分類とは」、受け渡しの要素「JS ad_stat」（値の名前 `ob_stat`）と、その値で回答データを書き換えるワークフロー。表示されない旧レイアウト「Group X」と旧ポップアップも含む。
  - HTML アプリ ob-map: 組織内分類と在籍・退職の画面のすべて（集計カード・マップ・詳細パネル・在籍・退職の見出し・タブ・一覧・変更ダイアログ・分析）を描く。データ用 HTML ob-data（自組織の回答データを 1 行 1 受験の文字列にしたもの）。
  - 管理画面ページの「Section: 組織内分類」（URL の `section` が「組織内分類」または「在籍・退職」のとき表示）、サイドメニュー（再利用要素「Page Sidebar - Hoverable Icons」）。
  - データ型「回答データ」（在籍区分・入社日・退職日・前回の回答・除外YesorNo・回答者情報-幹部）、「在籍記録」、オプションセット「OS_人ステータス」「OS_退職理由」。
  - お知らせの HTML「E」（在籍・退職の分析）、操作マニュアルの HTML「C」（4〜7 ページ）。
- 参照元の画面（2026-11-04）: オーナーでない管理者のアカウントで閲覧した、組織内分類（全員）と在籍・退職（分析・在籍者・退職者・在籍者の行の「変更」ダイアログ）。組織内分類を「在籍」「退職」に切り替えた画面、在籍・退職の「求職者」タブ、詳細パネル、「組織内分類とは」のポップアップは画面に写っておらず（取得に失敗）、定義から書いた（6 章）。画面の文字の大きさなどの一部は、スクリーンショットから測った値で書いた（§2.22 の表）。
- アプリと前回の仕様: リポジトリのパス（例 `lib/services/classification.ts`、`docs/基本設計/06_画面設計_管理者.md` §3.6）。

### 0.5 K-19 の置き換え

本書の画面の文言、4 分類の説明文、16 キャラクターの位置の説明・特徴・適性・適性職種、「組織内分類とは」の本文には、K-19 の置き換えの対象（院長（先生）・医院・クリニック・院長・幹部、歯科の職種・業務・用語）が無い（参照元定義の ob-map と再利用要素「組織内分類」の全文で確かめた）。置き換えが要るのは職業の表示だけで、参照元の職業（歯科の職種）ではなく、アプリの職業マスタ（00 §1.10。K-19・K-21 の 9 項目と、表示だけに使う旧コード 9「その他」）の表示名を出す。スペシャリストの適性職種の「病院」は付録C §1 のタイプの説明文で、K-19 の対象外（K-19 はタイプの説明文を変えない）。言い換えに迷う文言は無い。

### 2.2 数える「人」（zaiseki-08・09・10・M1）

参照元: 画面に渡すのは自組織の回答データのうち「除外YesorNo」が true でないもの（受験日の新しい順）。その中で、(1) いずれかの受験の「前回の回答」に指されている受験、(2) タイプが 16 種以外の受験、(3) 同じ受験者 User の 2 件目以降、を捨てた残りが「人」で、組織内分類・在籍・退職の数と一覧はすべてこの人から作る。データの検索に既存スタッフ（回答者情報-幹部）の条件は無い（参照元定義の ob-data と ob-map の load）。

アプリ: サーバの `listOrganizationPeople(ctx)`（`lib/services/organization-people.ts`。§3.6）が次の手順で人を作る。組織内分類と在籍・退職は同じ関数を使う。

1. `listResults({ viewer: ctx })`（02 §8.5。11-2 §3.11 で `previousResultId`・`employmentStatus`・`hiredOn`・`leftOn` を射影に足したもの）で、閲覧範囲の受験を全件読む（Q3／Q4。今のクエリ。オーナー以外は `respondentKind == "applicant"`）。
2. `selectCountedHeads(rows)`（`lib/services/person-chain.ts` に足す純関数。§3.7）:
   1. `isExcluded` が true の受験を除く（Q-24）。
   2. 残りを `buildPersonRows()`（11-2 §2.2）でまとめ、各行の代表の受験を取り出す。ほかの受験の前回になっている受験は代表にならない（Q-10）。
   3. 代表の `submittedAt` の降順（同じなら `resultId` の昇順。`buildPersonRows()` の行の順のまま）で返す。
3. 代表の受験の受検者を `getRespondentsByIds({ organizationId, respondentIds })`（100 件ずつ）で読む。受検者が無い・組織が違う・論理削除済みの代表は除き、`logger.warn("classification.respondent_missing", { requestId, resultId })` を出す（今の作り。氏名などは出さない）。
4. `aptitudeType` が 16 タイプに無い代表は除き、`logger.warn("classification.unknown_type", { requestId, resultId })` を出す（参照元も 16 タイプ以外の行を捨てる。アプリの `results` では起きない）。
5. 職業の表示名は `getOccupationLabel(occupationCode)`（`lib/masters/occupations.ts`）。未知のコード（`getOccupationLabel` が `RangeError` を投げる）は捕まえて `null`（画面は「—」）にし、`logger.warn("classification.unknown_occupation", { requestId, resultId })` を出す。
6. `OrganizationPerson[]`（§3.6）を返す。

- 人の値: タイプ・区分・入社日・退職日・受験日（`submittedAt`）は代表の受験の値、氏名・電話番号・職業・チームは代表の受験の受検者（`respondents`）の値（参照元: 前者は最新の受験、後者は最新の受験の受験者 User の値。同じ）。チームは `results.teamCode` の複製と同じ値（02 §10 の I-3）。
- 参照元: 代表を決めたあと、同じ受験者 User の 2 件目以降も捨てる／アプリ: 受検者と受験は 1 対 1 なので、この手順が無くても結果は同じ（zaiseki-M1）。
- 回答一覧（11-2 §2.2）と同じ関数でまとめるので、2 つの画面で「同じ人」は一致する。違いは、本書は除外した受験を先に除き、回答一覧は除外した受験も行に出すことだけ（どちらも参照元どおり）。最新の受験だけが除外されていると、その前回が人として数えられる（参照元どおり。回答一覧は除外をつながった全受験に書くので、通常は起きない）。

### 2.17 勤続の計算（zaiseki-21）

- 日付はすべて暦日 `YYYY-MM-DD` の文字列で扱い、時間帯の変換をしない（入社日・退職日は 11-2 §3.1 の形、基準日は §3.3 の `today`）。
- 終点: 退職した人 = 退職日、在籍中の人 = 基準日。一覧の求職者のタブも、入社日があれば基準日まで（参照元どおり）。
- 満了の月数 `completedMonths(入社日, 終点)` = (終点の年 − 入社の年) × 12 + (終点の月 − 入社の月) − (終点の日 < 入社の日 なら 1、そうでなければ 0)。
- 計算しない（`null`）: 入社日が無い、終点が無い、終点 < 入社日（文字列の比較でよい）。
- 表示 `formatTenure(月数)`: `null` →「—」。12 未満 →「{月数}か月」（0 は「0か月」）。12 以上 →「{月数 ÷ 12 の整数部}年」に、余り（月数 % 12）が 1 以上なら「{余り}か月」を続ける。
- 平均 `averageMonths(月数の並び)` = `Math.round(合計 ÷ 人数)`（月の整数。.5 は切り上げ）→ `formatTenure` で表示。人数 0 なら `null`（「—」）。
- 例（テストに使う）:

| 入社日 | 終点 | 月数 | 表示 |
|---|---|---:|---|
| 2026-10-14 | 2026-10-29 | 0 | 0か月 |
| 2020-04-01 | 2022-08-31 | 28 | 2年4か月 |
| 2023-04-01 | 2024-06-30 | 14 | 1年2か月 |
| 2024-01-31 | 2024-02-29 | 0 | 0か月 |
| 2024-02-29 | 2025-02-28 | 11 | 11か月 |
| 2024-02-29 | 2025-03-01 | 12 | 1年 |
| 2025-04-02 | 2026-04-01 | 11 | 11か月 |
| 2018-05-15 | 2026-11-15 | 102 | 8年6か月 |
| 2021-11-05 | 2026-11-05 | 60 | 5年 |

  平均の例: [1, 2] → 2、[0, 1] → 1、[5, 6] → 6（「6か月」）、[11, 12] → 12（「1年」）、[] → `null`（「—」）。
- 参照元: 「今日」はブラウザの今の日付（地域時刻）／アプリ: 基準日（Asia/Tokyo）。日本国内の利用では同じ日付になる（推定）。
